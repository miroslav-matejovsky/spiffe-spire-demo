Configuration and Management of SPIRE

SPIRE behavior is controlled by server.conf and agent.conf. The scenarios in this repository keep configurations intentionally small so you can see how trust domain, sockets, plugins, telemetry, and attestation settings fit together.

Configuration Format

SPIRE configuration files use HCL (HashiCorp Configuration Language) or JSON. In practice, most examples and nearly all files in this repository use HCL. The main files are server.conf for the SPIRE Server and agent.conf for each SPIRE Agent.

Server Configuration Reference

Core SPIRE Server settings live under the server { ... } block.

Option Description Typical or Default Value
trust_domain Required. Defines the root SPIFFE trust domain used for all issued identities. mirmat.org in this repository
bind_address Address the server listens on for agent connections. 0.0.0.0
bind_port Port used for agent-to-server communication. 8081
data_dir Required. Stores persistent state such as CA keys and the local database. Scenario-specific container path, commonly /opt/spire/data/server
socket_path Unix socket for SPIRE Server administrative APIs. /tmp/spire-server/private/api.sock
log_level Controls verbosity. DEBUG, INFO, WARN, or ERROR
log_format Controls structured output format. text or json
ca_key_type Selects the key algorithm for the upstream or local CA. ec-p256, ec-p384, rsa-2048, or rsa-4096
ca_ttl Lifetime of the SPIRE Server CA certificate. Often 24h in demos
default_x509_svid_ttl Default X.509 SVID lifetime. 1h
default_jwt_svid_ttl Default JWT-SVID lifetime. 5m
agent_ttl Lifetime for agent SVIDs and node credentials. Deployment-specific

Official reference: SPIRE Server configuration

Example server.conf from this repository

The following example is based on the production-like scenario and shows a server configured for both join_token and x509pop node attestation plus telemetry.

server {
    bind_address = "0.0.0.0"
    bind_port = "8081"
    socket_path = "/tmp/spire-server/private/api.sock"
    trust_domain = "mirmat.org"
    data_dir = "/opt/spire/data/server"
    log_level = "INFO"
    log_file = "/opt/spire/logs/spire.log"
    ca_ttl = "24h"
}

plugins {
    DataStore "sql" {
        plugin_data {
            database_type = "sqlite3"
            connection_string = "/opt/spire/data/server/datastore.sqlite3"
        }
    }
    NodeAttestor "join_token" {
        plugin_data {}
    }
    NodeAttestor "x509pop" {
        plugin_data {
            ca_bundle_path = "/opt/spire/conf/server/devid-ca.pem"
        }
    }
    KeyManager "memory" {
        plugin_data = {}
    }
}

telemetry {
    Prometheus {
        host = "spire-server"
        port = 8088
    }

    Statsd = [
        {
            address = "graphite-statsd:8125"
        },
    ]
}

Server Plugin Configuration

SPIRE Server features are extended through plugins. The following examples show the plugin types used most often when moving from local demos to real deployments.

DataStore sql

Used for persistent storage. SQLite is fine for demos, while PostgreSQL and MySQL are the common production choices.

DataStore "sql" {
    plugin_data {
        database_type = "postgres"
        connection_string = "dbname=spire user=spire password=secret sslmode=verify-full"
    }
}

KeyManager

  • memory for quick demos and ephemeral lab runs
  • disk for simple persistent storage
  • aws_kms when you want hardware-backed or managed key storage in production
KeyManager "disk" {
    plugin_data {
        keys_path = "/opt/spire/data/server/keys.json"
    }
}

KeyManager "aws_kms" {
    plugin_data {
        region = "eu-central-1"
        key_id = "arn:aws:kms:..."
    }
}

NodeAttestor

Node attestors prove what machine or platform is allowed to run an agent.

NodeAttestor "join_token" {
    plugin_data {}
}

NodeAttestor "x509pop" {
    plugin_data {
        ca_bundle_path = "/opt/spire/conf/server/devid-ca.pem"
    }
}

NodeAttestor "aws_iid" {
    plugin_data {
        access_key_id = "example"
        secret_access_key = "example"
    }
}

NodeAttestor "k8s_psat" {
    plugin_data {
        clusters = {
            demo = {
                service_account_allow_list = ["spire:spire-agent"]
            }
        }
    }
}

UpstreamAuthority

Use an upstream authority when SPIRE should mint intermediates instead of acting as the ultimate root.

UpstreamAuthority "disk" {
    plugin_data {
        cert_file_path = "/opt/spire/upstream/ca.crt"
        key_file_path = "/opt/spire/upstream/ca.key"
    }
}

UpstreamAuthority "vault" {
    plugin_data {
        vault_addr = "https://vault.example.org:8200"
        pki_mount_point = "pki"
        role = "spire-intermediate"
    }
}

UpstreamAuthority "aws_pca" {
    plugin_data {
        certificate_authority_arn = "arn:aws:acm-pca:..."
        region = "eu-central-1"
    }
}

UpstreamAuthority "spire" {
    plugin_data {
        server_address = "upstream-spire.example.org"
        server_port = "8081"
    }
}

Agent Configuration Reference

Option Description Typical or Default Value
trust_domain Required. Must match the SPIRE Server trust domain. mirmat.org
server_address Hostname or IP of the SPIRE Server. spire-server in the demo containers
server_port SPIRE Server control-plane port. 8081
socket_path Workload API socket path exposed to local workloads. /opt/spire/sockets/workload_api.sock in the demos
data_dir Local storage for agent state and keys. /opt/spire/data/agent
trust_bundle_path Path to the bootstrap trust bundle when not using insecure bootstrap. Scenario-specific file path
insecure_bootstrap Development-only shortcut for bootstrapping trust. true only in demo-style environments
log_level Controls agent logging verbosity. DEBUG, INFO, WARN, or ERROR
log_format Controls structured output format. text or json

Example agent.conf from this repository

This example is based on the metrics scenario and shows an agent using x509pop, a disk-backed key manager, and both Prometheus and StatsD telemetry.

agent {
    data_dir = "/opt/spire/data/agent"
    log_level = "INFO"
    log_file = "/opt/spire/logs/spire.log"
    server_address = "spire-server"
    server_port = "8081"
    socket_path ="/opt/spire/sockets/workload_api.sock"
    trust_bundle_path = "/opt/spire/conf/agent/bootstrap.crt"
    trust_domain = "mirmat.org"
}

plugins {
    NodeAttestor "x509pop" {
        plugin_data {
            private_key_path = "/opt/spire/conf/agent/agent.key.pem"
            certificate_path = "/opt/spire/conf/agent/agent.crt.pem"
        }
    }
    KeyManager "disk" {
        plugin_data {
            directory = "/opt/spire/data/agent"
        }
    }
    WorkloadAttestor "unix" {
        plugin_data {
        }
    }
}

telemetry {
    Prometheus {
        host = "spire-agent"
        port = 8089
    }

    Statsd = [
        {
            address = "graphite-statsd:8125"
        },
    ]
}

Telemetry Configuration

Telemetry is optional but strongly recommended for operations. SPIRE can expose Prometheus endpoints, push to StatsD, or emit DogStatsd metrics.

  • Prometheus: configure a host and port for the HTTP metrics endpoint.
  • StatsD: configure one or more collector addresses.
  • DogStatsd: configure a Datadog-compatible endpoint when that is your monitoring stack.

Official guide: Telemetry configuration

telemetry {
    Prometheus {
        host = "spire-server"
        port = 8088
    }

    Statsd = [
        {
            address = "graphite-statsd:8125"
        },
    ]

    DogStatsd = [
        {
            address = "datadog-agent:8125"
        },
    ]
}

Scenario 06 is the clearest repository example for telemetry because it wires SPIRE Server, SPIRE Agent, Prometheus, and Graphite/StatsD together in one compose stack.

Health Check Configuration

Health endpoints make it easier to drive readiness probes, container health checks, and startup orchestration.

health_checks {
    listener_enabled = true
    bind_address = "0.0.0.0"
    bind_port = "8080"
    live_path = "/live"
    ready_path = "/ready"
}

Use /live to confirm the process is running and /ready to confirm the component is actually ready to serve.

Registration Entry Management

Registration entries tell SPIRE which workloads or downstream agents can receive which SPIFFE IDs.

Official guide: Registering workloads and nodes

spire-server entry create \
  -spiffeID spiffe://mirmat.org/workload \
  -parentID spiffe://mirmat.org/spire/agent/join_token/worker-1 \
  -selector unix:uid:10001

spire-server entry show

spire-server entry update \
  -entryID <ENTRY_ID> \
  -spiffeID spiffe://mirmat.org/workload-v2 \
  -selector unix:uid:10002

spire-server entry delete -entryID <ENTRY_ID>

spire-server token generate -spiffeID spiffe://mirmat.org/spire/agent/join_token/worker-1
