Deployment Requirements and Guide

Use this page to prepare your workstation for the demo scenarios in this repository and to understand what changes when you move from a lab setup to a production SPIRE deployment. It also covers real-world deployment patterns where SPIRE agents run on Windows VMs and physical machines with limited network access, connecting to a centralized SPIRE server.

Environment-specific guides

For detailed deployment instructions with architecture diagrams and full configuration examples, see the environment-specific guides:

  • Hybrid Deployment - SPIRE Server in Azure (Linux container) + SPIRE Agent on Windows VM + business applications
  • On-Premises Deployment - SPIRE Server (Windows service) on VM + SPIRE Agents on separate Windows VMs across network segments

Prerequisites

To run the scenarios in this repository you need the following tools:

  • Podman and podman-compose for running every scenario stack in containers. Install guides: Podman and podman-compose.
  • Go 1.24+ for building scenario binaries and Go services. If you want to match the current repository tooling exactly, use the newest supported release from go.dev.
  • Task from taskfile.dev for repository build automation.
  • PowerShell for running the scenario scripts and local helper commands. Install guide: PowerShell installation.
Note

All scenarios in this repository run SPIRE inside containers. You do not need to install SPIRE locally on your host machine just to follow the demos.

Common gotcha

Run only one scenario at a time. Container names, socket volumes, and host ports overlap between scenarios and will conflict if another environment is still running.

SPIRE Server Requirements

For a production deployment, plan for a SPIRE Server host with these baseline requirements:

  • Operating system: Linux is recommended for the centralized SPIRE Server. Deploy it in a datacenter or cloud environment with stable network access and operational visibility.
  • Agent connectivity: all SPIRE Agents must be able to reach the server over port 8081.
  • Stable network path: maintain a stable WAN or VPN path so agents across remote sites can reach port 8081 reliably.
  • Persistent storage: keep the data_dir on durable storage so registration state and CA material survive restarts.
  • Production database: use PostgreSQL or MySQL in production. SQLite is suitable for development and testing only.
  • Compute resources: SPIRE is lightweight, but size CPU and memory for your agent count, signing load, and telemetry volume.

SPIRE Agent Requirements

  • One agent per VM or physical machine: every VM or physical machine that runs workloads should also run a SPIRE Agent [Agent config ref].
  • Server connectivity: outbound connectivity to the centralized SPIRE Server on port 8081. The connection may traverse WAN, VPN, or restricted network segments, and SPIRE handles reconnection automatically.
  • Service management: on Windows machines, the agent runs as a Windows service. On Linux, it typically runs as a systemd service.
  • Node attestation material: each agent needs whatever credentials its attestor requires, such as a join token, TPM material, or cloud metadata [Node attestation].
  • Workload API endpoint: local workloads need access to the local Workload API endpoint, exposed as a Unix domain socket on Linux or a named pipe on Windows [Workload endpoint spec].
  • Local SVID availability: the agent caches SVIDs locally, so workloads keep functioning during temporary server connectivity loss [Agent config ref].
  • Trust domain alignment: the agent must be configured for the same trust domain as the SPIRE Server.

Installation Methods

  • Container images: ghcr.io/spiffe/spire-server:1.15.0 and ghcr.io/spiffe/spire-agent:1.15.0
  • Binary releases: download official artifacts from the SPIRE GitHub releases page. For VM and physical machine deployments, download SPIRE binaries from GitHub releases and install the agent as a system service. This is the most common pattern for Windows servers and Linux VMs outside of container orchestrators [Getting started].
  • Helm charts: use the Kubernetes deployment options for environments that use Kubernetes.
  • Official guide: Install SPIRE Server

Quick Start with This Repository

  1. Clone the repository.
  2. Open a PowerShell terminal in the repository root.
  3. Build the binaries with task build.
  4. Start the first scenario with .\bin\scenario-01-simple.exe up.
  5. Use .\bin\scenario-01-simple.exe step if you want guided mode with pauses between major actions.
git clone https://github.com/miroslav-matejovsky/spiffe-spire-demo.git
cd spiffe-spire-demo

task build
.\bin\scenario-01-simple.exe up
.\bin\scenario-01-simple.exe step
.\bin\scenario-01-simple.exe down

If you prefer to inspect a later scenario after the initial walkthrough, replace scenario-01-simple.exe with any other scenario binary in the bin directory.

Deploying Agents on Windows

  • Download binaries: get the SPIRE Agent binary for Windows from the official GitHub releases page.
  • Create configuration directory: place the agent configuration in a dedicated path such as C:\spire\conf\agent.conf.
  • Use named pipes for Workload API: configure named_pipe_name instead of socket_path on Windows [Agent config ref].
  • Install as a service: register the agent as a Windows service with sc.exe or NSSM so it starts automatically.
  • Network path: make sure the machine has outbound access to the SPIRE Server on port 8081.
  • Bootstrap trust: provision the trust bundle before first startup so the agent can validate the centralized server [Server attestation].

Troubleshooting Common Issues

Port conflicts

If startup fails because a port is already in use, another scenario is probably still running. Stop it first, then retry.

Common gotcha

Bring the previous environment down before starting a new one. If you use scenario scripts directly, run the matching env-down.ps1 first.

Podman or podman-compose not found

Make sure both commands are installed and available on PATH. Open a new PowerShell session after installation so your shell picks up the updated environment.

Workload API socket mount issues

If workloads cannot fetch SVIDs, confirm the agent and workload containers share the same socket volume and that the socket path inside the workload matches SPIFFE_ENDPOINT_SOCKET or the application configuration.

Stale SPIRE data volumes

Old registration state, expired trust data, or half-finished lab runs can leave volumes in a bad state. Cleaning unused volumes often fixes repeated startup failures.

podman volume prune

Container build failures

If a scenario needs to build local Go binaries or images and the build fails, confirm your Go toolchain is new enough for the repository and that dependencies resolved cleanly with task build.

Agent cannot reach SPIRE Server

Check firewall rules, VPN status, and DNS resolution for the configured server address. The agent retries automatically, so inspect logs for connection timeout or TLS handshake errors while the path is unavailable.

SVIDs expire during server outage

Set availability_target in the agent configuration to at least 24h. The agent will pre-rotate SVIDs more aggressively so workloads can ride through expected downtime windows [Availability target].

Windows-specific problems

  • Use Windows path separators in PowerShell commands when working from the host.
  • Be careful with line endings if you edit scripts outside the repository defaults.
  • If bind mounts fail unexpectedly, verify the drive is shared correctly with your container runtime.

Connection refused on the Workload API

This usually means the SPIRE Agent is not ready yet or the workload socket was not mounted into the application container. Wait for the agent to attest, then re-check the shared volume and socket path.

Common gotcha

A Workload API error is often a startup ordering problem rather than an application bug. Make sure the agent has attested and created the socket before starting or testing workloads.
