Developer Guide: Implementing Workloads with the SPIFFE Workload API

The SPIFFE Workload API is the runtime interface workloads use to fetch identities, trust bundles, and validation data from a local SPIRE Agent. It is the normal path for application code that needs X.509-SVIDs, JWT-SVIDs, or automatic certificate rotation. See the Workload API spec, the Workload Endpoint spec, and SPIRE concepts.

Key idea

Applications do not talk to SPIRE Server directly. They talk to the local SPIRE Agent over local IPC, then use the returned SVIDs for mTLS or token-based authentication. In most Go applications, the best default is workloadapi.NewX509Source because it keeps identities fresh automatically. See go-spiffe/workloadapi.

1. Overview

The SPIFFE Workload API is a gRPC API served by the local workload endpoint. It provides X.509-SVIDs, JWT-SVIDs, trust bundles, and validation services to workloads at runtime. The endpoint is local to the host and is designed for identity bootstrapping, so workloads connect over local IPC rather than a normal remote network path. See the Workload API spec and the Workload Endpoint spec.

  • X.509-SVIDs: certificate chains plus private keys for mTLS workloads.
  • JWT-SVIDs: signed bearer tokens for HTTP APIs, message buses, and other non-TLS use cases.
  • Trust bundles: roots used to verify peers from one or more trust domains.
  • Streaming updates: gRPC streams let the endpoint push rotations and bundle changes as they happen. See Workload API section 4.3.

Workloads usually discover the endpoint from the standard SPIFFE_ENDPOINT_SOCKET environment variable. Conforming clients should use that value when no explicit address is configured. See Workload Endpoint section 4.

Tip

Keep application code focused on identity consumption, not identity storage. Let the agent own issuance, rotation, and trust bundle delivery.

2. Transport Options

The SPIFFE Workload Endpoint spec says the endpoint may use Unix Domain Sockets or TCP, and clients discover it through a URI such as unix:///... or tcp://127.0.0.1:8000. SPIRE Agent itself exposes local Unix sockets on Unix-like systems and named pipes on Windows. See the Workload Endpoint transport rules and the SPIRE Agent config reference.

Transport Platform URI Scheme SPIRE Agent Config Example
Unix Domain Socket Linux/macOS unix:// socket_path (default: /tmp/spire-agent/public/api.sock) unix:///opt/spire/sockets/workload_api.sock
Windows Named Pipe Windows npipe:// experimental.named_pipe_name (default: \\spire-agent\\public\\api) npipe:///spire-agent/public/api
TCP (localhost) All tcp:// Not supported natively by SPIRE Agent. Requires a proxy such as socat or Envoy in front of the local socket. tcp://127.0.0.1:8080

Unix Domain Socket

Unix Domain Sockets are the normal transport on Linux and macOS. They are local, efficient, and easy for the agent to protect with filesystem permissions and workload attestation rules. SPIRE Agent exposes the workload endpoint with socket_path, and examples often use the default /tmp/spire-agent/public/api.sock while this repository uses /opt/spire/sockets/workload_api.sock. See the Agent config reference.

Windows Named Pipe

Windows does not use Unix sockets, so SPIRE Agent exposes the same local endpoint through a named pipe. In URI form, clients use npipe:///spire-agent/public/api. In Windows native notation, the pipe is typically visible as \\.\pipe\spire-agent\public\api. The agent-side configuration uses experimental.named_pipe_name. The go-spiffe workloadapi package supports named pipe addresses.

TCP Through a Local Proxy

The Workload Endpoint spec allows TCP, but SPIRE Agent does not have a native TCP listener setting. That means there is no SPIRE config knob for tcp:// access. If a workload absolutely must use TCP, place a local proxy in front of the Unix socket or named pipe. Common choices are socat or Envoy. The proxy should only listen on loopback or another strongly authenticated local path. See the Workload Endpoint transport rules.

socat TCP-LISTEN:8199,fork UNIX-CONNECT:/tmp/spire-agent/public/api.sock
Warning

TCP transport should only be used when Unix sockets or named pipes are truly impossible. The SPIFFE spec requires strong network-level workload authentication (localhost only) when using TCP. SPIRE agent does not natively expose a TCP listener - you need a local proxy.

Transport facts

The Workload Endpoint spec says transport may be UDS or TCP, transport security must not require TLS, and every gRPC request must include metadata header workload.spiffe.io: true for SSRF protection. Official SDKs such as go-spiffe handle that header for you. Custom gRPC clients, such as a hand-built C# client, must add it explicitly. See Workload Endpoint section 3.

Locating the Endpoint

SPIFFE_ENDPOINT_SOCKET is the standard environment variable used to locate the workload endpoint. Use it unless you have a strong reason to hard-code the address. See Workload Endpoint section 4.

export SPIFFE_ENDPOINT_SOCKET=unix:///opt/spire/sockets/workload_api.sock
$env:SPIFFE_ENDPOINT_SOCKET = "npipe:///spire-agent/public/api"

3. Go Examples

Go has a first-class SDK in go-spiffe/workloadapi and TLS helpers in go-spiffe/spiffetls/tlsconfig. For long-running services, prefer source objects such as X509Source and JWTSource instead of one-shot fetches.

3a. Fetching X.509 SVIDs

package main

import (
    "context"
    "log"

    "github.com/spiffe/go-spiffe/v2/workloadapi"
)

func main() {
    ctx := context.Background()

    // Connect to Workload API
    // Uses SPIFFE_ENDPOINT_SOCKET env var if no address specified
    client, err := workloadapi.New(ctx,
        workloadapi.WithAddr("unix:///opt/spire/sockets/workload_api.sock"))
    if err != nil {
        log.Fatalf("failed to create workload API client: %v", err)
    }
    defer client.Close()

    // Fetch X.509 SVID
    svid, err := client.FetchX509SVID(ctx)
    if err != nil {
        log.Fatalf("failed to fetch SVID: %v", err)
    }

    log.Printf("SPIFFE ID: %s", svid.ID)
    log.Printf("Certificate expires: %s", svid.Certificates[0].NotAfter)
}

Use a direct fetch for small tools, diagnostics, or one-shot commands. For daemons and servers, use a source that stays connected and rotates automatically.

3b. X509Source with automatic rotation

// X509Source connects to Workload API and automatically
// fetches and rotates X.509 SVIDs in the background
x509Source, err := workloadapi.NewX509Source(ctx,
    workloadapi.WithClientOptions(
        workloadapi.WithAddr("unix:///opt/spire/sockets/workload_api.sock")))
if err != nil {
    log.Fatalf("unable to create X509Source: %v", err)
}
defer x509Source.Close()

svid, err := x509Source.GetX509SVID()
if err != nil {
    log.Fatalf("unable to get X509-SVID: %v", err)
}
log.Printf("SPIFFE ID: %s", svid.ID)

This is the recommended pattern for real services. The source opens a long-lived stream to the workload endpoint, keeps the current SVID set in memory, and updates it when the agent pushes new data. See Workload API section 4.3.

3c. mTLS server

package main

import (
    "context"
    "log"
    "net/http"

    "github.com/spiffe/go-spiffe/v2/spiffeid"
    "github.com/spiffe/go-spiffe/v2/spiffetls/tlsconfig"
    "github.com/spiffe/go-spiffe/v2/workloadapi"
)

func main() {
    ctx := context.Background()
    socketPath := "unix:///opt/spire/sockets/workload_api.sock"

    x509Source, err := workloadapi.NewX509Source(ctx,
        workloadapi.WithClientOptions(workloadapi.WithAddr(socketPath)))
    if err != nil {
        log.Fatalf("unable to create X509Source: %v", err)
    }
    defer x509Source.Close()

    td, _ := spiffeid.TrustDomainFromString("example.org")

    // MTLSServerConfig creates TLS config that:
    // - Uses SVID as server certificate (auto-rotated)
    // - Requires client certificates (mutual TLS)
    // - Authorizes clients from the specified trust domain
    tlsConfig := tlsconfig.MTLSServerConfig(
        x509Source, x509Source,
        tlsconfig.AuthorizeMemberOf(td))

    server := &http.Server{
        Addr:      ":8443",
        TLSConfig: tlsConfig,
    }

    // Empty cert/key paths - TLS config provides certificates
    log.Fatal(server.ListenAndServeTLS("", ""))
}

In this repository, cmd/svid-server/main.go uses the same pattern with trust domain mirmat.org, adds HTTP handlers, and extracts the client SPIFFE ID from the peer certificate for logging.

3e. JWT-SVID for non-TLS scenarios

package main

import (
    "context"
    "log"

    "github.com/spiffe/go-spiffe/v2/svid/jwtsvid"
    "github.com/spiffe/go-spiffe/v2/workloadapi"
)

func main() {
    ctx := context.Background()
    socketPath := "unix:///opt/spire/sockets/workload_api.sock"

    jwtSource, err := workloadapi.NewJWTSource(ctx,
        workloadapi.WithClientOptions(workloadapi.WithAddr(socketPath)))
    if err != nil {
        log.Fatalf("unable to create JWTSource: %v", err)
    }
    defer jwtSource.Close()

    svid, err := jwtSource.FetchJWTSVID(ctx, jwtsvid.Params{
        Audience: "spiffe://example.org/my-server",
    })
    if err != nil {
        log.Fatalf("unable to fetch JWT-SVID: %v", err)
    }
    log.Printf("JWT token: %s", svid.Marshal())
}

Use JWT-SVIDs when you need identity outside mTLS, such as HTTP bearer auth, RPC metadata, or message queue headers. The audience must match what the receiving service expects. See the Workload API spec.

3f. Windows named pipe example

x509Source, err := workloadapi.NewX509Source(ctx,
    workloadapi.WithClientOptions(
        workloadapi.WithAddr("npipe:///spire-agent/public/api")))

The go-spiffe SDK understands unix://, tcp://, and npipe:// addresses, so the application code stays mostly the same across platforms. See go-spiffe/workloadapi.

4. C# / .NET Examples

.NET does not have an official SPIFFE SDK today. The practical approach is to generate gRPC client stubs from the official workloadapi.proto, then connect to the local workload endpoint using the transport available on your platform.

No official C# SDK

There is no official C# SPIFFE SDK today. Java has an official implementation in java-spiffe, but .NET users usually generate client code from workloadapi.proto and handle transport details themselves.

4b. Unix Domain Socket (Linux, .NET 5+)

using System.Net.Sockets;
using Grpc.Net.Client;

var socketPath = "/opt/spire/sockets/workload_api.sock";
var udsEndPoint = new UnixDomainSocketEndPoint(socketPath);

var connectionFactory = new UnixDomainSocketsConnectionFactory(udsEndPoint);
var socketsHandler = new SocketsHttpHandler
{
    ConnectCallback = connectionFactory.ConnectAsync
};

using var channel = GrpcChannel.ForAddress("http://localhost", new GrpcChannelOptions
{
    HttpHandler = socketsHandler
});

var client = new SpiffeWorkloadAPI.SpiffeWorkloadAPIClient(channel);

// Add required SPIFFE metadata header
var headers = new Grpc.Core.Metadata
{
    { "workload.spiffe.io", "true" }
};

// Fetch X.509 SVIDs
using var call = client.FetchX509SVID(
    new X509SVIDRequest(), headers: headers);

await foreach (var response in call.ResponseStream.ReadAllAsync())
{
    foreach (var svid in response.Svids)
    {
        Console.WriteLine($"SPIFFE ID: {svid.SpiffeId}");
        // svid.X509Svid contains DER-encoded certificate chain
        // svid.X509SvidKey contains DER-encoded PKCS#8 private key
        // svid.Bundle contains DER-encoded trust bundle
    }
}

Helper class for the Unix connection factory:

public class UnixDomainSocketsConnectionFactory
{
    private readonly EndPoint _endPoint;

    public UnixDomainSocketsConnectionFactory(EndPoint endPoint)
    {
        _endPoint = endPoint;
    }

    public async ValueTask<Stream> ConnectAsync(
        SocketsHttpConnectionContext context,
        CancellationToken cancellationToken = default)
    {
        var socket = new Socket(AddressFamily.Unix, SocketType.Stream, ProtocolType.Unspecified);
        try
        {
            await socket.ConnectAsync(_endPoint, cancellationToken);
            return new NetworkStream(socket, ownsSocket: true);
        }
        catch
        {
            socket.Dispose();
            throw;
        }
    }
}

4c. Windows Named Pipe (.NET 6+)

using System.IO.Pipes;
using Grpc.Net.Client;

var pipeName = "spire-agent/public/api";

var socketsHandler = new SocketsHttpHandler
{
    ConnectCallback = async (context, cancellationToken) =>
    {
        var pipe = new NamedPipeClientStream(
            ".", pipeName,
            PipeDirection.InOut,
            PipeOptions.WriteThrough | PipeOptions.Asynchronous);

        await pipe.ConnectAsync(cancellationToken);
        return pipe;
    }
};

using var channel = GrpcChannel.ForAddress("http://localhost", new GrpcChannelOptions
{
    HttpHandler = socketsHandler
});

var client = new SpiffeWorkloadAPI.SpiffeWorkloadAPIClient(channel);

You still need the workload.spiffe.io: true metadata header on each call, just like the Unix socket example.

4d. TCP localhost (with proxy)

// If you set up a local proxy (socat) forwarding TCP to UDS:
// socat TCP-LISTEN:8199,fork UNIX-CONNECT:/tmp/spire-agent/public/api.sock

using var channel = GrpcChannel.ForAddress("http://127.0.0.1:8199");

var headers = new Grpc.Core.Metadata { { "workload.spiffe.io", "true" } };
// ... same FetchX509SVID call as above

Only do this when local IPC is unavailable. Keep the proxy bound to loopback and treat it as a privileged local service. See Workload Endpoint section 3.

5. Authorization Patterns

After mTLS succeeds, the next question is authorization. The tlsconfig helpers let you move from generic trust-domain checks to exact identity checks or fully custom rules.

Authorize any SPIFFE ID in a trust domain

td, err := spiffeid.TrustDomainFromString("example.org")
if err != nil {
    log.Fatal(err)
}

tlsConfig := tlsconfig.MTLSServerConfig(
    x509Source,
    x509Source,
    tlsconfig.AuthorizeMemberOf(td),
)

Authorize one exact SPIFFE ID

serverID, err := spiffeid.FromString("spiffe://example.org/my-server")
if err != nil {
    log.Fatal(err)
}

tlsConfig := tlsconfig.MTLSClientConfig(
    x509Source,
    x509Source,
    tlsconfig.AuthorizeID(serverID),
)

Authorize one of several exact SPIFFE IDs

id1, _ := spiffeid.FromString("spiffe://example.org/api")
id2, _ := spiffeid.FromString("spiffe://example.org/api-canary")

tlsConfig := tlsconfig.MTLSServerConfig(
    x509Source,
    x509Source,
    tlsconfig.AuthorizeOneOf(id1, id2),
)

Custom authorizer

authorizer := tlsconfig.Authorizer(func(id spiffeid.ID, chains [][]*x509.Certificate) error {
    if id.TrustDomain().String() != "example.org" {
        return fmt.Errorf("unexpected trust domain: %s", id.TrustDomain())
    }
    if !strings.HasPrefix(id.Path(), "/backend/") {
        return fmt.Errorf("unauthorized workload path: %s", id.Path())
    }
    return nil
})

tlsConfig := tlsconfig.MTLSServerConfig(x509Source, x509Source, authorizer)

Use custom authorization when you need business rules that are more specific than trust domain membership. Keep those rules simple and explicit. If the policy becomes large, move it into configuration rather than burying it in code.

6. SVID Rotation

SVID rotation is one of the main reasons to use the Workload API instead of loading certificates from files. With X509Source, the SDK keeps a streaming gRPC connection open, receives full updated responses from the agent, and swaps in new SVIDs and bundles as needed. Application code does not need to reload certificates manually. See Workload API section 4.3.

  • Automatic background updates: X509Source keeps the current SVID set fresh.
  • No restart required: the TLS config reads from the source during handshakes, so new connections use rotated credentials automatically.
  • Full-state updates: each stream response contains the full current set, not just deltas.
  • Redactions matter: if a later response removes an SVID or bundle, clients should stop using it.
Recommended pattern

Create one long-lived source per process and share it anywhere you need SPIFFE-based TLS or bundle lookups. Do not fetch a new SVID for every request.

7. Error Handling and Resilience

Workload code should expect temporary outages and policy timing issues. The Workload Endpoint and Workload API specs define the main error behaviors. See Workload Endpoint section 6.

Condition What it means What to do
Agent unavailable or socket missing The local endpoint is not reachable yet, is restarting, or is overloaded. Retry with backoff. Long-lived sources and clients should reconnect automatically.
Agent loses server connectivity The local agent cannot currently reach SPIRE Server. Keep using cached SVIDs and bundles while they remain valid. Plan availability_target and TTLs to cover expected outages.
PermissionDenied The workload has no registered identity yet, or policy has not propagated. Usually means the workload is not registered. Fix registration, then retry with backoff if eventual consistency is expected.
InvalidArgument The mandatory security header is missing or a required request field is invalid. Do not blindly retry. Fix the client. Custom gRPC callers must send workload.spiffe.io: true.
Unavailable The endpoint is up but cannot handle the request right now. Retry with backoff.
Operational rule

If you see PermissionDenied, check workload registration first. If you see InvalidArgument, check client implementation first. Only network or availability errors should trigger routine retry loops.

For long-running services, prefer source-based APIs because they already implement reconnect behavior and keep serving cached data when possible. Avoid writing your own tight reconnect loops around raw gRPC streams unless you truly need custom behavior.

8. Connecting to This Repository's Scenario 05

Scenario 05 in this repository is the working example for Workload API-based mTLS. See cmd/svid-server/main.go, cmd/svid-client/main.go, and the scenario assets under scenarios/05-svid-api/.

  • Shared endpoint: both binaries connect to unix:///opt/spire/sockets/workload_api.sock.
  • Automatic rotation: both use workloadapi.NewX509Source.
  • Server authorization: cmd/svid-server/main.go builds tlsconfig.MTLSServerConfig and authorizes any client in trust domain mirmat.org.
  • Client authorization: cmd/svid-client/main.go builds tlsconfig.MTLSClientConfig and authorizes servers in trust domain mirmat.org.
  • Workload registration: Scenario 05 registers identities for the server and client, then the application code simply consumes them through the Workload API.

That split is important: SPIRE handles attestation, registration, issuance, and rotation; the workload code only needs to consume identities and make authorization decisions. If you want a full end-to-end example, start with Scenario 05 and compare the code in cmd/svid-server/main.go and cmd/svid-client/main.go to the snippets above.
