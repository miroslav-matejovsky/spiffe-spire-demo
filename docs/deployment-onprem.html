On-Premises Deployment: All-Windows SPIRE

Deploy SPIRE Server and Agents as Windows services on VMs. Business applications run as Windows services on the same or separate VMs across different network segments or domains.

When to use this pattern

Use on-premises deployment when all infrastructure runs on Windows VMs or physical machines, typically in corporate datacenters, branch offices, or air-gapped environments. SPIRE Server runs on a central Windows VM, and agents run on separate machines across network segments.

Windows support is experimental

SPIRE Server and Agent support Windows named pipes under the experimental configuration block in v1.15.0. The functionality works but the configuration interface may change in future releases [Server config ref] [Agent config ref].

Architecture Diagram

SPIRE Server, Agent, and Business API share one VM. Client VMs on separate network segments each run their own Agent and Business Client. All components are Windows services. All Workload API endpoints are Windows named pipes.

SPIRE Server Setup (Windows)

SPIRE Server runs as a Windows service on a central VM. It uses the experimental named_pipe_name for the Server API instead of a Unix socket.

server {
    bind_address = "0.0.0.0"
    bind_port = "8081"
    trust_domain = "mirmat.org"
    data_dir = "C:\\spire\\data\\server"
    log_level = "INFO"
    log_format = "json"
    ca_ttl = "24h"

    experimental {
        named_pipe_name = "\\spire-server\\private\\api"
    }
}

plugins {
    DataStore "sql" {
        plugin_data {
            database_type = "sqlite3"
            connection_string = "C:\\spire\\data\\server\\datastore.sqlite3"
        }
    }
    KeyManager "disk" {
        plugin_data {
            keys_path = "C:\\spire\\data\\server\\keys.json"
        }
    }
    NodeAttestor "x509pop" {
        plugin_data {
            ca_bundle_path = "C:\\spire\\conf\\server\\agent-ca.pem"
        }
    }
    NodeAttestor "join_token" {
        plugin_data {}
    }
}
SQLite for small deployments only

SQLite works for small on-premises deployments with a single SPIRE Server. For high availability with multiple servers, use PostgreSQL or MySQL. See Production Guide.

Installing Server as Windows Service

# Install SPIRE Server as a Windows service
sc.exe create "SPIRE Server" binPath= "C:\spire\bin\spire-server.exe run -config C:\spire\conf\server\server.conf" start= auto
sc.exe start "SPIRE Server"

SPIRE Agent Setup (Server VM)

Agent on the Server VM uses the same trust domain and connects to the local server.

agent {
    data_dir = "C:\\spire\\data\\agent"
    log_level = "INFO"
    log_format = "json"
    server_address = "127.0.0.1"
    server_port = "8081"
    trust_bundle_path = "C:\\spire\\conf\\agent\\bootstrap.crt"
    trust_domain = "mirmat.org"

    experimental {
        named_pipe_name = "\\spire-agent\\public\\api"
    }
}

plugins {
    NodeAttestor "x509pop" {
        plugin_data {
            private_key_path = "C:\\spire\\conf\\agent\\agent.key.pem"
            certificate_path = "C:\\spire\\conf\\agent\\agent.crt.pem"
        }
    }
    KeyManager "disk" {
        plugin_data {
            directory = "C:\\spire\\data\\agent"
        }
    }
    WorkloadAttestor "windows" {
        plugin_data {
            discover_workload_path = true
        }
    }
}

SPIRE Agent Setup (Client VMs)

Agents on remote client VMs connect to the central SPIRE Server over the network. Set availability_target to handle network disruptions across segment boundaries.

agent {
    data_dir = "C:\\spire\\data\\agent"
    log_level = "INFO"
    log_format = "json"
    server_address = "spire-server.corp.local"
    server_port = "8081"
    trust_bundle_path = "C:\\spire\\conf\\agent\\bootstrap.crt"
    trust_domain = "mirmat.org"
    availability_target = "24h"

    experimental {
        named_pipe_name = "\\spire-agent\\public\\api"
    }
}

plugins {
    NodeAttestor "x509pop" {
        plugin_data {
            private_key_path = "C:\\spire\\conf\\agent\\agent.key.pem"
            certificate_path = "C:\\spire\\conf\\agent\\agent.crt.pem"
        }
    }
    KeyManager "disk" {
        plugin_data {
            directory = "C:\\spire\\data\\agent"
        }
    }
    WorkloadAttestor "windows" {
        plugin_data {
            discover_workload_path = true
        }
    }
}

Workload Registration

# Register Business API on the server VM
spire-server entry create \
    -spiffeID spiffe://mirmat.org/business-api \
    -parentID spiffe://mirmat.org/spire/agent/x509pop/<server-agent-fingerprint> \
    -selector windows:user_name:WORKGROUP\\ApiService

# Register Business Client on client VMs
spire-server entry create \
    -spiffeID spiffe://mirmat.org/business-client \
    -parentID spiffe://mirmat.org/spire/agent/x509pop/<client-agent-fingerprint> \
    -selector windows:user_name:WORKGROUP\\ClientService
Windows selector choices

Use windows:user_name or windows:user_sid to match by service account identity. Use windows:path (requires discover_workload_path = true) to match by executable path. Combine selectors for stronger matching -- all selectors on one entry use AND logic [windows plugin].

Network Requirements

  • Agent to Server: outbound TCP from each client VM to the Server VM on port 8081. Crosses network segment/domain boundaries.
  • Business Client to Business API: application-level port (e.g., 8443) from client VMs to server VM. mTLS secures the connection.
  • Named pipe access: local only. Business workloads access SPIRE Agent via named pipe on each VM. No network port needed.
  • No inbound ports on client VMs: all SPIRE connections are outbound from agents to server.

Server Node Attestor azure_imds + x509pop x509pop + join_token
Server DataStore Azure PostgreSQL SQLite (small) or PostgreSQL

Resilience and Operations

  • Set availability_target = "24h" (or longer) on all remote agents.
  • Use KeyManager "disk" everywhere so SVIDs survive restarts.
  • Place data_dir on persistent local disk on every VM.
  • Configure log_format = "json" and forward logs to your centralized log aggregation system.
  • Monitor agent-to-server connectivity and SVID expiry as key operational metrics.
  • For HA, deploy multiple SPIRE Servers behind a load balancer with a shared PostgreSQL database. See Production Guide.
