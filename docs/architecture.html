SPIRE Architecture and Components

SPIRE turns SPIFFE concepts into running infrastructure. It issues identities for workloads, distributes trust bundles, and makes those identities available over a local API instead of through static certificate files.

Overview

Core shape

SPIRE consists of a Server, one or more Agents, and the Workload API. Server acts as trust anchor and signing authority. One Agent runs on each VM or physical machine, connecting back to a centralized Server over the network. This hub-and-spoke pattern works well even with restricted or intermittent connectivity. Workloads connect to the local Workload API to fetch SVIDs and trust bundles.

SPIRE Server

Holds registration data, trust bundle state, and signing keys for trust domain.

SPIRE Agent

Attests node, caches workload SVIDs, and exposes local APIs over Unix sockets.

Workload API

Standard SPIFFE API used by applications and SDKs such as go-spiffe.

Architecture Diagram

Server signs identities for trust domain. Agent brokers access. Workloads never talk to server directly for day-to-day identity fetches. In typical deployments, Server sits in a datacenter or cloud with stable access, while Agents run on distributed VMs and physical machines.

SPIRE Server

SPIRE Server is central authority for trust domain. It stores registration entries, signs SVIDs using its CA key, performs node attestation, and publishes bundle material used to verify identities. Server typically runs centralized in a datacenter or cloud environment where it has stable network access, durable storage, and operational visibility. Agents across the organization connect to it over WAN or VPN links.

  • Central authority for trust domain and source of truth for registration state.
  • Stores registration entries that map selectors to SPIFFE IDs.
  • Signs agent and workload SVIDs using CA key.
  • Performs node attestation before an agent is trusted.
  • Exposes Registration API via Unix socket at /tmp/spire-server/private/api.sock.
Plugin model

Server behavior comes from plugins. Common choices are DataStore sql, KeyManager memory, disk, or aws_kms, NodeAttestor join_token, x509pop, aws_iid, or k8s_psat, and UpstreamAuthority disk, vault, or aws_pca.

SPIRE Agent

SPIRE Agent runs on every VM or physical machine that hosts workloads. It proves node identity to server, receives an agent SVID, fetches registration data, generates workload keys, and caches workload SVIDs close to processes that need them.

  • Runs on every VM or physical machine that hosts workloads.
  • Performs node attestation to prove identity to server.
  • Caches SVIDs for workloads so applications can fetch them locally.
  • Caches SVIDs locally so workloads continue to operate even when connectivity to the central server is intermittent or temporarily unavailable.
  • Exposes Workload API as Unix Domain Socket.
  • Performs workload attestation by checking PID, UID, process path, or service identity.
Agent plugins

Agent also uses plugins: NodeAttestor for proving node identity, WorkloadAttestor plugins such as unix, k8s, or docker, and KeyManager plugins for workload private keys.

In repo, Scenario 01 shows basic node bootstrap. Scenario 03 focuses on workload attestation and local identity delivery through agent.

Workload API

Workload API is SPIFFE standard API for applications. It is exposed by agent as Unix Domain Socket, typically at /tmp/spire-agent/public/api.sock. Applications do not parse agent cache directly. They call API methods such as FetchX509SVID, FetchJWTSVID, and bundle fetch operations.

Workload --unix socket--> SPIRE Agent Workload API

Common calls:
- FetchX509SVID
- FetchX509Bundles
- FetchJWTSVID
- FetchJWTBundles

go-spiffe wraps API for Go applications and handles watchers, source updates, and identity parsing. Agent also pushes updated SVIDs before expiry so workloads get auto-rotation without restart. Scenario 05 in repo demonstrates this model with mTLS client and server.

Why local socket matters

Workloads only need access to local agent socket. This is especially important for machines with limited or intermittent server connectivity. The agent's local cache ensures workloads can fetch and use valid SVIDs even during server outages or network disruptions. Workloads never need direct access to the central SPIRE server. Identity checks stay tied to local process context.

SVID Issuance Flow

Below is typical day-in-life flow from cold start to workload identity fetch.

1

Server boots

Server starts and generates self-signed CA for trust domain, or uses UpstreamAuthority to chain to external CA.

2

Agent attests node

Agent starts and performs node attestation by sending proof such as join token, X.509 proof-of-possession, or cloud metadata.

3

Server issues agent SVID

Server validates proof and returns agent SVID plus bundle data.

4

Agent reconnects with mTLS

Agent now talks to server over authenticated gRPC mTLS.

5

Registration data arrives

Agent fetches registration entries that describe which workloads are allowed to receive which SPIFFE IDs.

6

Agent builds CSRs

Agent generates key pairs for workloads and sends certificate signing requests to server.

7

Server signs workload identities

Server signs CSRs and returns workload SVIDs.

8

Agent caches results

Agent stores workload SVIDs and bundle material in local cache and exposes them through Workload API. This local cache is critical -- workloads keep functioning with cached SVIDs even if the connection to the central server drops.

9

Workload requests identity

Workload calls Workload API. Agent checks PID, UID, or container metadata to find matching selectors.

10

Agent returns cached SVID

Agent returns matching cached SVID and keeps it rotated before expiry.

Plugin Architecture

SPIRE stays flexible by defining narrow plugin types. Same control plane can fit Windows servers, Linux VMs, physical machines, and containerized environments by swapping plugin implementations.

Plugin Type Purpose Example Plugins
DataStore Persists registration entries, bundles, and server state. sql
KeyManager Creates and stores signing keys or workload keys. memory, disk, aws_kms
NodeAttestor Verifies node identity before issuing agent SVID. join_token, x509pop, aws_iid, k8s_psat
WorkloadAttestor Maps local process or container properties to selectors. unix, systemd, docker
UpstreamAuthority Signs SPIRE CA with external or higher-level CA. disk, vault, aws_pca
Notifier Signals external systems when bundle data changes. k8sbundle
BundlePublisher Publishes trust bundles to external distribution targets. disk, aws_s3, gcs
