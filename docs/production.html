Production Deployment Best Practices

Moving from demo or lab to production needs deliberate choices around security, reliability, and observability. This page shows what changes between the demo scenarios in this repository and a real production deployment.

Demo vs Production

Aspect Demo (This Repo) Production
Database SQLite PostgreSQL or MySQL
Key Management memory disk, AWS KMS, Vault, Azure Key Vault
Bootstrap insecure_bootstrap=true trust_bundle_path or trust_bundle_url
Node Attestation join_token, x509pop Platform-native (aws_iid, k8s_psat, tpm_devid)
High Availability Single server Multiple servers plus shared DB
Monitoring Optional (scenario 06) Required (Prometheus plus alerting)
Log Format text json for log aggregation
SVID TTLs Defaults Tuned per environment
CA Self-signed UpstreamAuthority (Vault, AWS PCA, and similar)

Database

Do not use SQLite in production

SQLite is fine for demos and single-node labs. Production deployments need a networked SQL backend so multiple SPIRE servers can share state and survive host failures.

  • PostgreSQL is the usual recommendation for production SPIRE deployments.
  • MySQL is also supported when it fits your environment better.
  • The database user needs permissions such as INSERT and DROP so SPIRE can manage its schema.
  • Regular backups are essential because the datastore contains registration, bundle, and node state.
plugins {
  DataStore "sql" {
    plugin_data {
      database_type = "postgres"
      connection_string = "host=postgres.example.net port=5432 dbname=spire user=spire password=change-me sslmode=verify-full"
    }
  }
}

Key Management

Do not use in-memory KeyManager in production

The server signing key is extremely sensitive. If it is compromised, an attacker can forge workload and agent identities across your trust domain.

  • disk: minimum acceptable production baseline because keys survive restarts.
  • aws_kms: HSM-backed option and strong default for AWS deployments.
  • azure_key_vault: Azure Managed HSM integration is available in SPIRE v1.15.0.
  • vault: HashiCorp Vault Key Manager is new in SPIRE v1.15.0 and fits centralized secrets operations.

Upstream Authority (CA Integration)

A self-signed root is acceptable for isolated environments, but enterprise deployments usually connect SPIRE to an existing PKI. Use an UpstreamAuthority plugin when you need SPIRE server intermediates signed by a corporate or cloud CA.

Common options include disk, aws_pca, vault, gcp_cas, spire for nested SPIRE, and cert-manager.

plugins {
  UpstreamAuthority "vault" {
    plugin_data {
      vault_addr = "https://vault.example.org/"
      pki_mount_point = "pki"
      ca_cert_path = "/etc/spire/vault-ca.pem"
      token_auth {
        token = "<vault-token>"
      }
    }
  }
}

Secure Bootstrap

Never use insecure_bootstrap=true in production

Bootstrap trust must come from a secure channel. Otherwise, a man-in-the-middle can impersonate your SPIRE server and own the identity system from first contact.

  • Distribute the trust bundle with secure file copy or configuration management.
  • Or use trust_bundle_url over valid HTTPS with a certificate chain your agents already trust.
  • Plan key generation and storage before the first production install.
openssl ecparam -name prime256v1 -genkey -noout -out spire-root-ca.key
openssl req -x509 -new -key spire-root-ca.key -sha256 -days 3650 -out spire-root-ca.crt -subj "/CN=SPIRE Root CA"

Node Attestation Best Practices

  • Prefer platform-native attestation such as aws_iid, gcp_iit, or k8s_psat where possible.
  • Join tokens are acceptable for some controlled bootstrap flows, but they should be single-use and tightly managed.
  • For bare-metal or edge systems, evaluate x509pop, sshpop, or tpm_devid.
  • Security note: the aws_iid PKCS7 path had a critical CVE fixed in v1.14.6, so keep attestation plugins current.

High Availability

  • Run multiple SPIRE servers behind stable addressing with shared PostgreSQL or MySQL.
  • Use nested SPIRE when you need geographic distribution or delegated operational control.
  • Set agent availability_target to at least 24h so workloads can tolerate temporary server downtime without immediate identity disruption.

SVID TTL Tuning

  • X.509 SVID default is 1h. Shorter TTLs improve security but increase signing load.
  • JWT SVID default is 5m. Keep JWT TTLs short because there is no revocation channel.
  • CA TTL default is 24h. It should stay significantly longer than your SVID TTLs.
  • ca_key_type = ec-p256 is the default and a good balance for most deployments.

Monitoring and Observability

Use scenario 06 as lab practice, then make observability mandatory in production.

  • Enable Prometheus metrics on both server and agent.
  • Expose health endpoints such as /live and /ready.
  • Enable audit_log_enabled when you need compliance and traceability.
  • Set log_format = json for centralized log aggregation.
  • Watch key signals such as SVID signing rate, attestation failures, and cache size.

Security Hardening Checklist

  • [ ] No insecure_bootstrap
  • [ ] No memory KeyManager
  • [ ] No SQLite in production
  • [ ] Proper trust bundle distribution
  • [ ] Platform-native node attestation
  • [ ] UpstreamAuthority configured
  • [ ] Rate limiting enabled (default)
  • [ ] Server API socket not exposed to network
  • [ ] Workload API socket permissions restricted
  • [ ] Monitoring and alerting configured
  • [ ] Log aggregation enabled (json format)
  • [ ] Regular key rotation policy
  • [ ] SVID TTLs reviewed and tuned
  • [ ] Post-quantum TLS considered (require_pq_kem)

Federation

Federation enables cross-trust-domain communication. You publish a bundle endpoint, exchange trust bundles, and let workloads from separate trust domains validate each other without sharing one trust root.

server {
  federation {
    bundle_endpoint {
      address = "0.0.0.0"
      port = 8443
      profile "https_web" {}
    }

    federates_with "partner.example" {
      bundle_endpoint_url = "https://partner.example:8443"
      bundle_endpoint_profile "https_web" {
        endpoint_spiffe_id = "spiffe://partner.example/spire/server"
      }
    }
  }
}
