Networking, Ports, and Security Considerations

SPIRE uses a small set of network paths. In hub-and-spoke deployments, agents on remote VMs and physical machines need only one outbound port to reach the centralized SPIRE Server. All connections are agent-initiated - the server never connects back to agents. Most sensitive interfaces are local Unix domain sockets or named pipes, while the agent-to-server control plane uses mutually authenticated gRPC. [SPIFFE Concepts overview]

Network Architecture

Key design: agent-initiated connections only

All SPIRE network connections are initiated by agents toward the server. The SPIRE Server never opens connections back to agents. This means agents only need outbound access to the server, and no inbound ports are required on agent machines. This design works well in restricted environments, behind NAT, and without VPN tunnels.
SPIFFE Docs: Agent Concepts

  • Agent-to-Server (outbound, port 8081): each SPIRE Agent initiates a gRPC connection to the SPIRE Server. The agent connects outbound on port 8081 using mTLS. The server never connects back to agents. This is critical for restricted networks - agents only need one outbound port open. [Agent config reference]
  • Agent-to-Workload (local IPC): workloads on the same machine connect to the agent through a Unix Domain Socket (Linux) or Named Pipe (Windows). No TCP port is required. [SPIFFE Workload Endpoint spec]
  • Automatic reconnection: when connectivity drops, agents automatically retry with exponential backoff. Workloads continue using cached SVIDs during outages. No manual intervention needed. [Availability target docs]
  • Dashboard-to-Server: Unix Domain Socket access through a shared volume mounted at the SPIRE Server API socket path.
  • External access: the demo dashboard is exposed on port 8080 in most scenarios so you can inspect SPIRE state from a browser.
Design choice

The most privileged interfaces stay off the network. In these demos, the browser reaches only the dashboard, while the dashboard itself talks to the SPIRE Server through a shared Unix socket.

Local IPC: Unix Domain Sockets and Named Pipes

Two local IPC endpoints matter most in SPIRE deployments. On Linux, these are Unix Domain Sockets. On Windows, SPIRE uses named pipes instead.

  • Server API socket: /tmp/spire-server/private/api.sock (Linux) or \\.\pipe\spire-server\private\api (Windows) for administrative and dashboard access to SPIRE Server APIs.
  • Workload API socket: /tmp/spire-agent/public/api.sock (Linux) or \\.\pipe\spire-agent\public\api (Windows). This repository uses /opt/spire/sockets/workload_api.sock in demos.

On Linux, containers share these sockets through named volumes. On Windows, named pipes are accessible by name to processes on the same machine. That is why the dashboard can talk to the server without opening a remote admin port, and why demo workloads can fetch SVIDs without using the network.

Applications usually discover the workload socket through the SPIFFE_ENDPOINT_SOCKET environment variable or an explicit socket path in configuration.

Firewall Rules

  • Server: allow inbound 8081 from all authorized agents.
  • Agents: allow outbound traffic to server:8081.
  • Dashboard: allow inbound 8080 only if you intentionally expose the web UI.
  • Metrics: allow 8088, 8089, and 9090 only on your monitoring network or within the container network.
  • Workload API: no firewall ports are needed because it is a Unix socket (Linux) or named pipe (Windows), not a TCP listener. On Windows, protect named pipe access with Windows ACLs.

Hub-and-Spoke Networking

A common production topology keeps the centralized SPIRE Server in a datacenter or cloud environment while agents run on distributed VMs and physical machines across remote sites. All connections are agent-initiated outbound. No VPN tunnels or reverse connections are needed.

  • Outbound only from agents: agents initiate gRPC connections to server:8081. No inbound ports are required on agent machines. The server passively listens and never dials agents. [SPIFFE Docs: Agent]
  • NAT and firewall friendly: since connections are outbound from agent to server, they work through NAT gateways and firewalls without special configuration.
  • Minimal firewall surface: in very restrictive environments, only port 8081 needs to be allowed outbound from agent hosts to the server address.
  • Load balancers: SPIRE v1.15.0 supports PROXY protocol for deployments behind compatible load balancers. [Server config reference]

Handling Unstable Connectivity

  • Automatic retry: agents reconnect automatically with exponential backoff when the server path is interrupted.
  • Cached identities: during server disconnection, the agent continues serving cached SVIDs to local workloads.
  • availability_target: set it based on expected downtime windows, with a minimum of 24h, so the agent pre-rotates SVIDs before disconnects.
  • sync_interval: this experimental setting controls how often the agent synchronizes with the server.
  • Best practice: size availability_target for your worst-case server outage window, not just normal operations.
  • Persistent cache: SVID cache survives agent restarts when the disk KeyManager is used.

Security Considerations

  • TLS: all server-agent communication uses mTLS, so both sides authenticate each other.
  • Bootstrap trust: agents need an initial trust bundle or bootstrap mode before they can validate the server. insecure_bootstrap = true is for development only.
  • Workload API access control: protect the socket with file permissions, workload attestors, and careful PID or namespace boundaries.
  • Windows Workload API: on Windows machines, SPIRE Agent uses named pipes instead of Unix domain sockets. Protect named pipe access with Windows ACLs.
  • Rate limiting: SPIRE rate-limits sensitive operations such as node attestation and signing to reduce abuse and accidental overload.
  • PROXY protocol support: SPIRE v1.15.0 can preserve client IP information behind supported load balancers.
  • Central server protection: in hub-and-spoke deployments, the centralized server is the highest-value target. Place it in a well-protected network segment with access logging and monitoring.
  • Post-quantum TLS: the require_pq_kem option can require hybrid key exchange such as X25519MLKEM768 where supported.
Danger

Never expose the SPIRE Server API socket to untrusted networks. It is an administrative interface and should stay on a protected local socket or tightly controlled internal path.

Danger

Never use insecure_bootstrap in production. Replace it with a real trust bundle distribution path or a stronger node attestation flow.
