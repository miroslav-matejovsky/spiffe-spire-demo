Core SPIFFE/SPIRE Concepts

SPIFFE defines identity model. SPIRE implements it. Once core terms are clear, rest of system becomes much easier to reason about.

Official references

Keep SPIFFE concepts and registration entry docs close while learning. They explain naming rules, bundle formats, and API behavior in detail.

SPIFFE ID

SPIFFE ID is workload identity string. It uses URI format spiffe://trust-domain/path. Trust domain names identity provider boundary. Path carries workload-specific meaning and is usually organized to match teams, namespaces, services, or environments.

spiffe://example.org/web-server
spiffe://prod.acme.com/ns/default/sa/api
spiffe://mirmat.org/svid-client
spiffe://corp.example/datacenter-east/payment-service
spiffe://corp.example/remote-site/win-server-01/inventory-app
  • Trust domain is like DNS domain in shape, but it does not need DNS resolution.
  • Path is hierarchical and conventionally represents organizational structure, physical site, machine role, or application identity.
  • Maximum trust domain length is 255 characters.
Naming hint

Good SPIFFE IDs are stable and boring. Put human-readable ownership in path. Avoid encoding ephemeral instance details into identity path unless policy really needs it.

SVID (SPIFFE Verifiable Identity Document)

SVID is concrete credential bound to SPIFFE ID. SPIRE can issue X.509-SVIDs for mutual TLS and JWT-SVIDs for token-based systems.

Type Format Primary use Default TTL Notes
X.509-SVID X.509 certificate mTLS and certificate-based auth 1 hour Auto-rotated by agent, key type is ec-p256 by default, used in Scenario 05.
JWT-SVID JWT token Bearer-token auth and service-to-service API calls 5 minutes Contains sub, aud, and exp. Short TTL matters because JWT-SVIDs cannot be revoked.

X.509-SVID

X.509-SVID is normal-looking certificate with SPIFFE ID carried in SAN URI field. Peers verify certificate chain against trust bundle and read identity from URI SAN, not from Common Name.

Certificate:
  Subject: CN=
  Subject Alternative Name:
    URI:spiffe://example.org/web-server
  Issuer: CN=SPIRE Server CA
  Key Usage: Digital Signature, Key Encipherment
  Extended Key Usage: TLS Web Client Authentication, TLS Web Server Authentication
  Validity:
    Not Before: 2025-01-01T12:00:00Z
    Not After : 2025-01-01T13:00:00Z

Scenario 05 shows X.509-SVID use end to end with Go services and mTLS.

JWT-SVID

JWT-SVID is signed token with SPIFFE ID in sub claim, audience in aud, and expiry in exp. It is useful when transport is not mTLS-friendly or when upstream services already expect bearer tokens.

{
  "sub": "spiffe://example.org/web-server",
  "aud": ["payments-api"],
  "exp": 1735747500
}

More background lives in official SPIFFE concepts docs.

Trust Domain

Trust domain is root of trust for one identity provider boundary. All workloads inside same trust domain ultimately chain back to same CA material and share same SPIFFE ID prefix.

  • Configured in server.conf and agent.conf. Values must match.
  • Examples: prod.acme.com, staging.acme.com, partner.org.
  • Repo uses trust domain mirmat.org.
  • Federation lets workloads trust identities from foreign trust domains without merging them.
Boundary rule

Changing trust domain is identity-breaking change. Every SPIFFE ID changes. Treat it like moving to new certificate authority boundary.

Trust Bundle

Trust bundle is collection of public keys and root certificates used to verify SVIDs for one trust domain. Server auto-generates bundle on first startup, then agents and workloads use it to verify peers.

  • Used to verify SVIDs from matching trust domain.
  • Agents get initial bundle through trust_bundle_path or insecure_bootstrap.
  • Bundle rotation is automatic. Agents fetch updates from server.
  • Federation bundles are bundles imported from foreign trust domains.
Mental model

SVID is leaf identity. Trust bundle is verification material. One proves who peer says it is. Other proves why you should believe it.

Registration Entries

Registration entry maps SPIFFE ID to selectors. It also defines parent ID, which tells SPIRE which agent is allowed to issue that identity. All selectors on one entry use AND logic, so workload must satisfy every listed selector.

  • Maps one SPIFFE ID to one or more selectors.
  • Parent ID restricts which agent can mint identity.
  • Created with spire-server entry create.
  • Repo references: Scenario 03 register-workload.ps1, Scenario 05 register-workloads.ps1.
spire-server entry create \
  -spiffeID spiffe://mirmat.org/svid-server \
  -parentID spiffe://mirmat.org/spire/agent/join_token/worker-1 \
  -selector unix:uid:10001

spire-server entry create \
  -spiffeID spiffe://mirmat.org/svid-client \
  -parentID spiffe://mirmat.org/spire/agent/join_token/worker-1 \
  -selector unix:uid:10002

More details: SPIFFE registration guide.

Node Attestation

Node attestation is how agent proves it belongs to infrastructure you trust. Different attestors match different environments and threat models.

Method Typical platform How identity is proven Security level
x509pop VMs or hosts with existing PKI Proof of possession for existing X.509 certificate Strong
tpm_devid Hardware-backed hosts TPM DevID certificate anchored in hardware Very strong
join_token Labs, demos, initial bootstrap One-time pre-shared token issued by server Basic
aws_iid AWS EC2 AWS Instance Identity Document signed by AWS Strong
k8s_psat Kubernetes Projected service account token bound to cluster issuer Strong
VM and physical machine hint

For VM and physical machine environments, x509pop (certificate-based) and tpm_devid (TPM hardware) are the strongest choices. They work without cloud-provider metadata and bind agent identity to durable machine credentials.

Workload Attestation

Workload attestation is how local process proves what it is so agent can choose matching registration entry. In traditional VM and physical machine deployments, the most important inputs are local process identity and service metadata rather than cluster metadata.

Attestor type Available selectors Common use
unix uid, gid, process path, sometimes supplementary process details Primary choice for Linux services and workloads on VMs or physical machines
systemd service name, unit metadata, and related host service attributes Primary choice for long-running Linux services managed by systemd
docker container labels, image, container ID Container-focused selector matching outside Kubernetes
k8s namespace, service account, pod labels, pod UID Optional choice for Kubernetes-native identity policy

Repo uses unix workload attestation in Scenario 03 and Scenario 05. Agent checks calling PID, UID, and process path on local socket before returning identity. For Windows services, agents can match workloads by process properties so long-running machine-based services still map cleanly to registration entries.

Certificate Rotation

SPIRE automates credential lifecycle. Agents monitor SVID expiry and renew before half-life, then push updates through Workload API streams so applications do not need manual reload logic. Rotation resilience also matters in conservative infrastructure: agent-managed local caches let workloads continue using valid SVIDs during temporary server disconnection, and agent renews them when connectivity is restored.

1

Agent tracks expiry

Agent watches TTL on cached SVIDs and trust bundles.

2

Renew before half-life

Before halfway point, agent asks server for fresh credentials. If link to central server is temporarily down, cached SVIDs remain available locally until connectivity returns.

3

Stream updates

Updated SVIDs are streamed to workloads through Workload API watchers.

4

No downtime

Applications keep using refreshed identity without restart or manual certificate reload.

// go-spiffe sources handle rotation for you.
source, err := workloadapi.NewX509Source(ctx)
if err != nil {
    return err
}
defer source.Close()
