Hybrid Deployment: Azure Server + Windows VM Agent

Deploy SPIRE Server as a Linux container in Azure while running SPIRE Agents as Windows services on Windows VMs not connected to a domain. Business applications run as Windows services alongside the agent.

When to use this pattern

Use hybrid deployment when the centralized SPIRE Server runs in cloud infrastructure (Azure, AWS, or similar) and agents are distributed across Windows VMs in remote sites, branch offices, or standalone machines without Active Directory domain membership.

Architecture Diagram

SPIRE Server runs centralized in Azure. Business API runs alongside an agent in Azure. Windows VM runs its own agent (Windows service) with business client workloads. All agent-to-server connections are outbound.

Component Summary

SPIRE Server Setup (Azure)

Deploy SPIRE Server as a Linux container in Azure Container Instances, Azure Kubernetes Service, or a Linux VM. Use Azure Database for PostgreSQL as the datastore and Azure Key Vault for key management.

server {
    bind_address = "0.0.0.0"
    bind_port = "8081"
    socket_path = "/tmp/spire-server/private/api.sock"
    trust_domain = "mirmat.org"
    data_dir = "/opt/spire/data/server"
    log_level = "INFO"
    log_format = "json"
    ca_ttl = "24h"
}

plugins {
    DataStore "sql" {
        plugin_data {
            database_type = "postgres"
            connection_string = "host=spire-db.postgres.database.azure.com port=5432 dbname=spire user=spire password=<secret> sslmode=verify-full"
        }
    }
    KeyManager "azure_key_vault" {
        plugin_data {
            key_vault_uri = "https://spire-keyvault.vault.azure.net/"
            key_identifier_file = "/opt/spire/data/server/azure_key_id"
        }
    }
    NodeAttestor "azure_imds" {
        plugin_data {
            tenants = {
                "<azure-tenant-id>" = {
                    resource_groups = ["spire-agents-rg"]
                }
            }
        }
    }
    NodeAttestor "x509pop" {
        plugin_data {
            ca_bundle_path = "/opt/spire/conf/server/agent-ca.pem"
        }
    }
    NodeAttestor "join_token" {
        plugin_data {}
    }
}

Official reference: SPIRE Server configuration, azure_key_vault plugin, azure_imds plugin

SPIRE Agent Setup (Azure - Linux)

Agent running alongside Business API in Azure. Uses Azure node attestation and Unix workload attestation.

agent {
    data_dir = "/opt/spire/data/agent"
    log_level = "INFO"
    log_format = "json"
    server_address = "spire-server.internal"
    server_port = "8081"
    socket_path = "/opt/spire/sockets/workload_api.sock"
    trust_bundle_path = "/opt/spire/conf/agent/bootstrap.crt"
    trust_domain = "mirmat.org"
}

plugins {
    NodeAttestor "azure_imds" {
        plugin_data {}
    }
    KeyManager "disk" {
        plugin_data {
            directory = "/opt/spire/data/agent"
        }
    }
    WorkloadAttestor "unix" {
        plugin_data {
            discover_workload_path = true
        }
    }
}

SPIRE Agent Setup (Windows VM)

Agent runs as a Windows service on a VM not connected to a domain. Uses x509pop or join_token for node attestation and the windows WorkloadAttestor for identifying local workloads.

Named pipe is experimental

The named_pipe_name setting is still experimental in SPIRE v1.15.0. It is functional but the configuration interface may change in future releases [Agent config ref].

agent {
    data_dir = "C:\\spire\\data\\agent"
    log_level = "INFO"
    log_format = "json"
    server_address = "spire-server.example.com"
    server_port = "8081"
    trust_bundle_path = "C:\\spire\\conf\\agent\\bootstrap.crt"
    trust_domain = "mirmat.org"
    availability_target = "24h"

    experimental {
        named_pipe_name = "\\spire-agent\\public\\api"
    }
}

plugins {
    NodeAttestor "x509pop" {
        plugin_data {
            private_key_path = "C:\\spire\\conf\\agent\\agent.key.pem"
            certificate_path = "C:\\spire\\conf\\agent\\agent.crt.pem"
        }
    }
    KeyManager "disk" {
        plugin_data {
            directory = "C:\\spire\\data\\agent"
        }
    }
    WorkloadAttestor "windows" {
        plugin_data {
            discover_workload_path = true
        }
    }
}

Installing Agent as Windows Service

# Install SPIRE Agent as a Windows service using sc.exe
sc.exe create "SPIRE Agent" binPath= "C:\spire\bin\spire-agent.exe run -config C:\spire\conf\agent\agent.conf" start= auto
sc.exe start "SPIRE Agent"

# Or use NSSM for more control over service management
nssm install "SPIRE Agent" "C:\spire\bin\spire-agent.exe" "run -config C:\spire\conf\agent\agent.conf"
nssm set "SPIRE Agent" AppDirectory "C:\spire"
nssm start "SPIRE Agent"

Workload Registration

Register both Business API (Linux) and Business Client (Windows) as workloads on the SPIRE Server.

# Register Business API (Linux workload, unix attestor)
spire-server entry create \
    -spiffeID spiffe://mirmat.org/business-api \
    -parentID spiffe://mirmat.org/spire/agent/azure_imds/<tenant-id>/<sub-id>/<vm-id> \
    -selector unix:uid:10001

# Register Business Client (Windows workload, windows attestor)
spire-server entry create \
    -spiffeID spiffe://mirmat.org/business-client \
    -parentID spiffe://mirmat.org/spire/agent/x509pop/<agent-fingerprint> \
    -selector windows:user_name:WORKGROUP\\BusinessSvc

Official reference: Registering workloads, windows WorkloadAttestor selectors

Network Requirements

  • Azure to Azure: SPIRE Agent in Azure reaches Server on port 8081 over internal network. No public exposure needed.
  • Windows VM to Azure: outbound access from Windows VM to SPIRE Server on port 8081 over WAN or VPN. All connections are agent-initiated. No inbound ports needed on the Windows VM.
  • Business Client to Business API: mTLS connection between workloads. Firewall must allow the application port (e.g., 8443) from Windows VM to Azure.
  • Named pipe access: Business Client accesses SPIRE Agent via named pipe on localhost. No network port needed.

Resilience Considerations

  • Set availability_target = "24h" (or longer) on the Windows agent to handle WAN/VPN outages [Availability target].
  • Use KeyManager "disk" on the Windows agent so SVIDs survive agent restarts.
  • Place data_dir on persistent local storage on the Windows VM.
  • Agent reconnects automatically with exponential backoff when connectivity is restored.
  • Workloads keep using cached SVIDs during server outages.
