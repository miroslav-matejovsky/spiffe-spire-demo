Server API Guide

Use SPIRE Server API when you need to manage registration entries, agents, bundles, and other control-plane state. It is an administrative interface for SPIRE itself, not the API workloads use to fetch identity. Server config reference

Overview

The API is normally reached over a local Unix Domain Socket at /tmp/spire-server/private/api.sock or a named pipe on Windows. It is not exposed over the network by default, which is a deliberate security choice because this socket can create, update, and delete trusted identity state. Official docs

Primary interface

spire-server CLI is the usual operator entry point, while automation and dashboards can talk to the same API over gRPC. For generated clients and proto packages, use the official SPIRE API SDK.

Server API vs Workload API

These two APIs sit at different trust boundaries and solve different problems. The Server API manages SPIRE state. The Workload API delivers identity material to workloads without long-lived secrets. SPIRE concepts

Aspect Server API Workload API
Purpose Manage SPIRE (entries, agents, bundles) Deliver identity to workloads
Access Administrative - restricted Any authorized workload
Transport Unix socket / named pipe to server Unix socket / named pipe to agent
Authentication Admin socket requires local access Workload attestation (no secrets needed)
Users Operators, automation, dashboards Application code
Location Co-located with SPIRE Server Co-located with SPIRE Agent

CLI-based management

Most day-to-day administration starts with spire-server. The CLI wraps Server API operations and stays easiest for manual workflows, incident response, and bootstrap scripts. CLI reference

Registration entry management

Registration entries bind selectors to SPIFFE IDs and define who is allowed to receive which SVIDs. Concepts

# Create a registration entry
spire-server entry create \
    -spiffeID spiffe://example.org/my-workload \
    -parentID spiffe://example.org/agent \
    -selector unix:uid:1000

# List entries
spire-server entry show

# Delete an entry
spire-server entry delete -entryID <entry-id>

# Update an entry
spire-server entry update \
    -entryID <entry-id> \
    -spiffeID spiffe://example.org/my-workload \
    -selector unix:uid:1000 \
    -selector unix:path:/usr/bin/myapp

Agent management

Agent operations cover bootstrap, inventory, and cleanup. Join tokens are common in demos, but production often uses stronger node attestors. CLI reference

# Generate a join token
spire-server token generate -spiffeID spiffe://example.org/agent-host1

# List agents
spire-server agent list

# Evict an agent
spire-server agent evict -spiffeID spiffe://example.org/agent-host1

Bundle management

Bundles contain trust anchors for local or federated trust domains. Server operators inspect and publish them through the same administrative surface. SPIRE concepts

# Show current bundle
spire-server bundle show

# Set a federated bundle
spire-server bundle set -id spiffe://partner.org -path /path/to/partner-bundle.pem
Operator caution

Entry changes take effect immediately for issuance and authorization behavior. Treat CLI access like cluster-admin access and keep shell history, automation logs, and socket permissions under control. Server config reference

Programmatic access in Go

For services and tooling, use gRPC clients generated from the official SPIRE API SDK. This is how dashboards, operators, and automation jobs can create or inspect entries without shelling out to the CLI.

Using the SPIRE API SDK

Connect to the local Server API socket, then use typed clients such as EntryClient, AgentClient, and BundleClient. Server proto definitions

package main

import (
    "context"
    "log"

    entryv1 "github.com/spiffe/spire-api-sdk/proto/spire/api/server/entry/v1"
    "github.com/spiffe/spire-api-sdk/proto/spire/api/types"
    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"
)

func main() {
    ctx := context.Background()

    conn, err := grpc.Dial(
        "unix:///tmp/spire-server/private/api.sock",
        grpc.WithTransportCredentials(insecure.NewCredentials()),
    )
    if err != nil {
        log.Fatalf("failed to connect: %v", err)
    }
    defer conn.Close()

    entryClient := entryv1.NewEntryClient(conn)

    _, err = entryClient.BatchCreateEntry(ctx, &entryv1.BatchCreateEntryRequest{
        Entries: []*types.Entry{
            {
                SpiffeId: &types.SPIFFEID{
                    TrustDomain: "example.org",
                    Path:        "/my-workload",
                },
                ParentId: &types.SPIFFEID{
                    TrustDomain: "example.org",
                    Path:        "/agent",
                },
                Selectors: []*types.Selector{
                    {Type: "unix", Value: "uid:1000"},
                },
            },
        },
    })
    if err != nil {
        log.Fatalf("failed to create entry: %v", err)
    }
}

Listing entries

List operations are useful for inventory views, reconciliation loops, and dashboards that display current SPIRE state. Server proto definitions

listResp, err := entryClient.ListEntries(ctx, &entryv1.ListEntriesRequest{})
if err != nil {
    log.Fatalf("failed to list entries: %v", err)
}

for _, entry := range listResp.Entries {
    fmt.Printf("ID: %s, SPIFFE ID: spiffe://%s%s\n",
        entry.Id,
        entry.SpiffeId.TrustDomain,
        entry.SpiffeId.Path)
}
Windows note

On Windows, the Server API uses a named pipe instead of a Unix socket. The gRPC client pattern stays same, but transport setup must dial the named pipe endpoint configured for SPIRE Server. Server config reference

C# and .NET programmatic access

Like the Workload API case, there is no official first-party .NET SDK for the Server API. Standard approach is to generate gRPC clients from the proto files in spire-api-sdk/proto/spire/api/server, then connect over a Unix socket or named pipe.

using System.Net.Sockets;
using Grpc.Net.Client;

var socketPath = "/tmp/spire-server/private/api.sock";
var udsEndPoint = new UnixDomainSocketEndPoint(socketPath);

var handler = new SocketsHttpHandler
{
    ConnectCallback = async (context, ct) =>
    {
        var socket = new Socket(AddressFamily.Unix, SocketType.Stream, ProtocolType.Unspecified);
        await socket.ConnectAsync(udsEndPoint, ct);
        return new NetworkStream(socket, ownsSocket: true);
    }
};

using var channel = GrpcChannel.ForAddress("http://localhost", new GrpcChannelOptions
{
    HttpHandler = handler
});

var entryClient = new Entry.EntryClient(channel);

var response = await entryClient.ListEntriesAsync(new ListEntriesRequest());
foreach (var entry in response.Entries)
{
    Console.WriteLine($"SPIFFE ID: spiffe://{entry.SpiffeId.TrustDomain}{entry.SpiffeId.Path}");
}
Proto source

Generate only the services you need first, usually entry, agent, and bundle APIs. That keeps generated code small and easier to version with your service or internal admin tool. Server proto definitions

Building services with SVID-based authentication

Common pattern is a central service running near SPIRE Server while remote workloads run on agent-managed machines. Each remote workload authenticates with an SVID obtained from its local SPIRE Agent, and the central service validates that identity during mTLS before authorizing access. TLS config helpers

  • Central service gets its own SVID from the Workload API.
  • Clients on other machines get their own SVIDs from their local agents.
  • mTLS proves service identity on both sides.
  • Authorization uses SPIFFE IDs, not hostnames, API keys, or shared secrets.
package main

import (
    "context"
    "fmt"
    "log"
    "net/http"

    "github.com/spiffe/go-spiffe/v2/spiffeid"
    "github.com/spiffe/go-spiffe/v2/spiffetls/tlsconfig"
    "github.com/spiffe/go-spiffe/v2/workloadapi"
)

const workloadAPISocket = "unix:///tmp/spire-agent/public/api.sock"

type clientIDContextKey struct{}

func main() {
    ctx := context.Background()

    x509Source, err := workloadapi.NewX509Source(
        ctx,
        workloadapi.WithClientOptions(workloadapi.WithAddr(workloadAPISocket)),
    )
    if err != nil {
        log.Fatalf("create X509 source: %v", err)
    }
    defer x509Source.Close()

    serverSVID, err := x509Source.GetX509SVID()
    if err != nil {
        log.Fatalf("fetch server SVID: %v", err)
    }

    trustDomain := spiffeid.RequireTrustDomainFromString("example.org")
    allowedIDs := []spiffeid.ID{
        spiffeid.RequireFromString("spiffe://example.org/payments-client"),
        spiffeid.RequireFromString("spiffe://example.org/reporting-client"),
    }

    responses := map[spiffeid.ID]string{
        allowedIDs[0]: "payments export",
        allowedIDs[1]: "reporting snapshot",
    }

    tlsConfig := tlsconfig.MTLSServerConfig(
        x509Source,
        x509Source,
        tlsconfig.AuthorizeMemberOf(trustDomain),
    )

    mux := http.NewServeMux()
    mux.Handle("/data", spiffeAuthMiddleware(allowedIDs, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        clientID := r.Context().Value(clientIDContextKey{}).(spiffeid.ID)
        fmt.Fprintf(w, "server=%s\nclient=%s\ndata=%s\n", serverSVID.ID, clientID, responses[clientID])
    })))

    server := &http.Server{
        Addr:      ":8443",
        Handler:   mux,
        TLSConfig: tlsConfig,
    }

    log.Printf("serving as %s on https://0.0.0.0:8443", serverSVID.ID)
    log.Fatal(server.ListenAndServeTLS("", ""))
}

func spiffeAuthMiddleware(allowedIDs []spiffeid.ID, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.TLS == nil || len(r.TLS.PeerCertificates) == 0 {
            http.Error(w, "no client certificate", http.StatusUnauthorized)
            return
        }

        if len(r.TLS.PeerCertificates[0].URIs) == 0 {
            http.Error(w, "missing SPIFFE ID", http.StatusUnauthorized)
            return
        }

        clientID, err := spiffeid.FromURI(r.TLS.PeerCertificates[0].URIs[0])
        if err != nil {
            http.Error(w, "invalid SPIFFE ID", http.StatusUnauthorized)
            return
        }

        for _, allowed := range allowedIDs {
            if clientID == allowed {
                ctx := context.WithValue(r.Context(), clientIDContextKey{}, clientID)
                next.ServeHTTP(w, r.WithContext(ctx))
                return
            }
        }

        http.Error(w, "unauthorized SPIFFE ID", http.StatusForbidden)
    })
}
Why pattern works

SPIRE handles issuance and rotation, mTLS proves both peers, and application code only has to map SPIFFE IDs to policy. That makes authorization stable even when certificates rotate. go-spiffe TLS helpers

Security considerations

  • Server API socket is admin-level access. Protect it with strict filesystem permissions and process isolation. Server configuration file
  • Never expose Server API directly over the network unless you add a separate authentication and authorization layer in front of it.
  • Delegated Identity API allows agents to fetch SVIDs on behalf of workloads when architecture requires that separation. SPIRE concepts
  • admin_socket_path enables elevated local access. Keep it even more tightly controlled than read-only or app-facing sockets. Server configuration file
Do not treat Server API like app API

Server API can change trust relationships for whole environment. If a workload only needs its own SVID or trust bundle, use Workload API instead. Reserve Server API for operators, dashboards, and tightly controlled automation.
