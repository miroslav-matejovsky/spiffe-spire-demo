# Scenario 04 — TPM-Based Node Attestation

> **Complexity:** Intermediate · **Previous:** [03-workload](../03-workload/README.md) · **Next:** [05-svid-api](../05-svid-api/README.md)

This scenario teaches the **idea** of TPM-backed node identity in SPIRE.

To keep the demo runnable on ordinary container setups, it uses the SPIRE `x509pop` NodeAttestor as a **practical stand-in** for `tpm_devid`. The configuration, certificate hierarchy, and attestation flow are intentionally explained in TPM terms so you can understand how a real `swtpm` or hardware TPM deployment would work.

## What You Will Learn

- What a TPM is and why hardware-rooted identity matters
- What DevID means in the context of machine identity
- How SPIRE performs node attestation
- How certificate-based proof-of-possession maps to TPM DevID concepts
- Why TPM-style attestation is stronger than a join token

## Background Concepts

### What is a TPM?

A **Trusted Platform Module (TPM)** is a security device designed to protect keys and support attestation. In a real deployment it gives you three useful properties:

- **Protected key storage** — private keys are created and used inside the TPM
- **Proof of possession** — the machine can prove it controls a specific device-bound key
- **Measured trust signals** — platform state can be represented through TPM measurements such as PCR values

For learning and testing, a software TPM such as **swtpm** emulates the TPM 2.0 interfaces that a real machine would expose.

### Why use TPM for node attestation?

In a simple lab, a SPIRE agent can join with a **token**. That is easy, but it proves only that the agent knows a secret.

A TPM-based flow is stronger because the agent identity is tied to a device-bound key. The server is no longer trusting a reusable secret; it is trusting proof bound to a particular machine identity.

### DevID in plain language

**DevID** comes from IEEE 802.1AR. It gives a device an X.509 identity.

- **IDevID** — manufacturer-installed identity
- **LDevID** — locally issued identity, typically by the operator or platform owner

For SPIRE TPM node attestation, the important idea is simple: the agent presents a certificate chain rooted in a CA the server trusts, and proves control of the associated private key in a TPM-aware way.

### Where `swtpm` fits

In a full TPM lab, `swtpm` would emulate the TPM device. Provisioning would create a DevID key and certificate inside that TPM-backed environment, and SPIRE would use the `tpm_devid` NodeAttestor to verify it.

That full setup is possible, but it is much heavier and more brittle in portable container demos. This scenario therefore uses a certificate-based stand-in that is easier to run while still teaching the right mental model.

## Important Demo Note

This scenario is a **working simulation of the TPM certificate flow**, not a full TPM hardware attestation lab.

| Real TPM / `tpm_devid` | This scenario / `x509pop` |
|---|---|
| DevID key lives in TPM hardware or `swtpm` | DevID-like key is generated by the provisioning script |
| Server trusts the DevID CA | Server trusts the generated CA bundle |
| Agent proves TPM-backed possession of the DevID key | Agent proves certificate private-key possession |
| Requires TPM device wiring into the agent runtime | Works in ordinary containers |

Use this scenario to understand the **trust model** first. Then replace `x509pop` with `tpm_devid` when you are ready to integrate a real TPM or `swtpm` device.

## Architecture

```text
+---------------------------+                +---------------------------+
|       SPIRE Server        |                |        SPIRE Agent        |
|---------------------------|                |---------------------------|
| NodeAttestor: x509pop     |<-- attests --> | NodeAttestor: x509pop     |
| Trusts: devid-ca.pem      |                | Uses: devid-cert.pem      |
|                           |                |       devid-key.pem       |
+---------------------------+                +---------------------------+
            ^                                                   ^
            |                                                   |
            |                                   generated by    |
            +------------------- provision-tpm.ps1 -------------+

Real-world TPM mapping:
- devid-ca.pem      -> DevID issuing CA trusted by SPIRE Server
- devid-cert.pem    -> Device certificate analogous to a DevID
- devid-key.pem     -> Stand-in for a TPM-protected private key
- x509pop           -> Runnable proof-of-possession substitute for tpm_devid
```

## Scenario Files

- `compose.yml` — starts SPIRE Server and SPIRE Agent with the runnable `x509pop` setup
- `spire/server/server.conf` — server configuration with `x509pop` NodeAttestor
- `spire/agent/agent.conf` — agent configuration using the generated DevID-like credentials
- `tpm/Containerfile.agent` — optional extension point for a future `swtpm`-enabled agent image
- `tpm/provision-tpm.ps1` — generates the CA, agent certificate, and agent private key
- `scripts/env-up.ps1` — provisions credentials if needed and starts the scenario
- `scripts/env-down.ps1` — stops the scenario containers

## Prerequisites

- Windows with PowerShell 7+
- [Podman](https://podman.io/) and `podman-compose`

The provisioning script uses built-in .NET cryptography APIs, so no separate OpenSSL installation is required.

## Run the Scenario

Open a PowerShell terminal and switch to this directory:

```powershell
Set-Location .\scenarios\04-tpm
```

### 1. Provision the DevID-like credentials

```powershell
.\tpm\provision-tpm.ps1
```

This generates:

- `spire\server\devid-ca.pem`
- `spire\server\devid-ca-key.pem`
- `spire\agent\devid-cert.pem`
- `spire\agent\devid-key.pem`

### 2. Start the environment

```powershell
.\scripts\env-up.ps1
```

The script also auto-runs provisioning if the credentials are missing.

### 3. Verify node attestation

```powershell
podman-compose exec spire-server /opt/spire/bin/spire-server agent list
```

You should see an attested agent entry in the server output.

### 4. Inspect logs if you want more detail

```powershell
podman-compose logs -f -t
```

## How the Demo Maps to Real TPM Attestation

1. `provision-tpm.ps1` creates a CA and an agent certificate pair.
2. The SPIRE Server trusts that CA through `ca_bundle_path`.
3. The SPIRE Agent starts with the matching certificate and private key.
4. The `x509pop` attestor proves possession of that key.
5. The server accepts the agent because the certificate chains back to the trusted CA.

In a real TPM deployment, steps 1 and 4 would be TPM-aware:

- the key would be created inside the TPM or `swtpm`
- the private key would not simply exist as a regular PEM file
- the `tpm_devid` plugin would verify TPM-specific attestation evidence

## Join Token vs TPM-Style Attestation

| Aspect | Join Token | TPM / DevID Style |
|---|---|---|
| What is trusted | Shared secret | Device identity |
| Secret reuse risk | Higher | Lower |
| Hardware binding | No | Yes |
| Demo complexity | Low | Higher |
| Production suitability | Limited | Stronger |

## Why `tpm\Containerfile.agent` Is Still Included

The live compose stack uses the official SPIRE agent image so the scenario stays portable. The `tpm\Containerfile.agent` file is included as the obvious place to evolve this demo into a richer lab. In a more advanced version, that image is where you would add:

- `swtpm`
- `tpm2-tools`
- provisioning steps for a real emulated TPM device
- a switch from `x509pop` to `tpm_devid`
